# CEVRA Agent Rules

These rules are authoritative for Codex, Claude Code, and any other coding agent working in this repository.

Before substantial implementation, architecture work, review, or product research, read `docs/CEVRA_MASTER_CONTEXT.md` in full. `docs/ARCHITECTURE_V1.md` and accepted ADRs remain the specific architectural authorities; the master context connects their decisions and records current milestones without replacing them. Update the master context after a material merge, accepted decision, active-work transition, or completed research finding, preferably in a dedicated documentation change. Keep verified facts separate from inferences, and never rely on a chat thread as the only record of an agreed direction.

1. Read `docs/ARCHITECTURE_V1.md` before making architectural changes.
2. `packages/project-ir` is the canonical editable audiovisual project model. UI and engines are never sources of truth.
3. Do not add or replace a framework, engine, database, persistence model, update mechanism, or architectural pattern without an ADR and explicit product-owner approval.
4. Agents may invoke only typed, validated editing operations. Do not expose arbitrary shell commands or arbitrary FFmpeg filtergraphs from the end-user editing surface.
5. Every user-visible string must be internationalized. PT-BR and EN-US are mandatory and feature-parity must be maintained.
6. Desktop and mobile must share domain types, Project IR, design tokens and terminology where practical.
7. External engines and providers must be accessed behind stable CEVRA interfaces/adapters.
8. Project schemas are versioned. Backwards compatibility is preserved by explicit tested migrations.
9. Audit licenses before adding dependencies. Prefer Apache-2.0, MIT and BSD. LGPL/GPL/AGPL/proprietary/UNLICENSED require explicit review before implementation.
10. EDVID MIT code may be reused with required attribution. Auroq or other proprietary/UNLICENSED code may be studied for behavior and architecture but must be independently reimplemented unless a compatible license is obtained.
11. Never commit secrets, API keys, access tokens, signing keys or private model credentials.
12. CEVRA-owned source is proprietary unless a file explicitly states otherwise. Third-party notices belong in `THIRD_PARTY_LICENSES.md` and `NOTICE`.
13. Every editing mutation must generate an auditable journal entry and recoverable state/snapshot.
14. Before a material architectural change, present the proposal, benefit, risk and impact for product-owner approval.
15. Do not silently replace approved engines: Media, Composition, Transcription, QA, Agent Bridge, Persistence, Update or Secure Storage.
16. External dependency updates are never blindly applied. Validate compatibility and run tests before release.
17. Preserve a clean adapter boundary so future OpenCut, Premiere, Resolve, cloud providers or local generation engines can be added without changing Project IR.
18. The application must remain usable without an AI agent for manual editing/review tasks supported by the UI.
19. Content Intelligence is a separate optional domain within CEVRA Orbit. Do not store source records, signals, ideas, briefs, scripts, performance observations or content memory in Project IR merely to associate them with an audiovisual project.
20. Instagram, YouTube, TikTok, publishing services, analytics vendors, AI vendors and similar systems are always provider/adapter implementations. Provider-native schemas must not become core domain models.
21. CEVRA Vids must remain functional without Content Intelligence, Marketplace, unimplemented Orbit services, paid AI APIs or external agents/providers.
22. Specialized content profiles (for example health/medical, business or creator) belong in versioned configuration/skill/policy packs, not in generic Content Intelligence core logic.
23. Code from external content-intelligence products may be reused only after exact license/provenance audit confirms compatibility with CEVRA's proprietary commercial distribution. Otherwise use independent/clean-room implementation.
24. Workflow / Production Presets are declarative application-level orchestration. They may resolve only to typed, validated CEVRA commands/providers and must never embed arbitrary code, shell commands, raw FFmpeg arguments/filtergraphs or credentials.
25. Built-in and user-created presets use the same versioned schema, capability checks and privilege boundary. Presets never replace Project IR or bypass journal/history.
26. CEVRA Orbit is the ecosystem boundary. CEVRA Vids and future products remain independent domains; shared Orbit services must not become a monolithic product core.
27. The public MIT EDVID project is the initial Vids functional baseline. Reuse requires exact provenance and attribution; branding and trade dress must not be copied. Intentional behavior changes are documented as `DIVERGÊNCIA EDVID` with parity or superiority evidence.
28. HyperFrames, Remotion and future composition engines remain behind `CompositionEngineAdapter`. A default requires the benchmark defined by ADR 0012; no engine is mandatory before parity evidence exists.
29. Future packages are signed, versioned and capability-limited. Third-party packages receive no arbitrary shell, network or filesystem access by default.
30. Editing and rendering work must preserve the non-destructive policy in ADR 0013. Original sources are immutable; proxies, previews, caches and intermediates never become final-quality sources or Project IR sources of truth. Final export uses original sources and assets whenever technically applicable. Quality and productivity are co-equal constraints: avoid unnecessary generational re-encoding and silent quality downgrade, and preserve EDVID parity unless a documented `DIVERGÊNCIA EDVID` proves equal or better behavior.
31. Keep the tracked repository intentionally clean, traceable and minimal, with no duplicate source of truth. Do not commit scratch files, dumps, logs, temporary exports, local caches, generated comparison files, backups or investigation artifacts without an explicit canonical reason. Keep heavy research media and screenshots outside the repository unless they are required versioned inputs. Before removing a tracked file, verify references, provenance, license/legal obligations, compatibility and architectural or historical value; accepted ADRs, required provenance, relevant audits, notices, licenses and necessary evidence are retained. Prefer an archive or external storage when historically valuable material does not belong in the active tree. Remove temporary branches locally and remotely after merge or closeout unless retention has an explicit purpose, and treat a historical branch fully incorporated by a successor as a deletion candidate only after confirming it has no useful unique content. Never perform opportunistic destructive cleanup inside an unrelated feature.
32. For composition and creative effects, keep the **untrusted boundary typed and validated** without over-typing internal implementation. Agents, presets and third-party packages may select only registered capabilities/components with schema-validated parameters and may never inject executable code. First-party internal components may use audited engine code behind the CEVRA component registry/Composition Compiler. Do not add a Project IR type or command per effect unless a real domain-state requirement demands it; engine-native code/state remains derived.
33. Stable/release packaging must satisfy Core Runtime Closure: do not ship a release that silently omits a mandatory runtime, engine, asset or minimum model required by advertised core behavior. Separate downloads are for optional/heavy packs unless the Product Owner explicitly approves a mandatory bootstrap after measured size/cost review.
34. V1 behavioral telemetry is NoOp by default. Crash diagnostics require opt-in, strict allow-list/redaction and must exclude project/media/prompt/transcript content. Never enable session/screen replay in V1.
35. Distinguish **CEVRA Bridge Skill** from **CEVRA Creator Skill**. Bridge supports CEVRA Vids requests to external agents and may only return/consume the typed Agent Protocol; it is not a standalone editor and cannot bypass Project IR/history/engines. Creator is a standalone agent-native editor product surface.
36. CEVRA Creator Lite and Full must share one editorial/creative/QA core rather than fork behavior. Full must be capable of final render/export without CEVRA Desktop. Reuse Project IR/domain/runtime/composition/UI packages where practical; when host constraints require a subset, keep it versioned and convertible rather than inventing incompatible audiovisual semantics.
37. Social publishing and social-performance analytics are post-V1 integrations. Local file export is core and must remain fully functional without social providers, app-review approvals, social tokens or Content Intelligence.

## Editorial decisions and product-wide refinement

Before work affected by editorial understanding, take selection, duration, pacing, junction planning, strategy, color or audio, read `docs/CEVRA_EDITORIAL_DECISIONS.md` together with the applicable Director record and discussion policy. Respect each decision's approval, dependency and validation status; product direction is not implementation closeout. These rules describe coordinated planning with shared evidence, not independent analysis or mutation systems. Respect the record's pending documentation-integration status until reconciled with the actual repository state.

Before presenting a material proposal anywhere in CEVRA Orbit, compare and refine alternatives for user-visible quality, processing/RAM/storage, latency, AI and infrastructure cost, complexity, maintenance/support and commercial eligibility. Recommend the simplest option that meets the required quality without silently shifting disproportionate cost into later work. State material trade-offs and uncertainty; use proportionate tests instead of unsupported performance or superiority claims.

Any component, including the Director, may be improved for a concrete reason. Preserve approved foundations unless evidence justifies change; obtain product-owner approval before material changes, record dated SUPERSEDED/refined decisions and reconcile affected records, ADRs and tests. This is not blanket permission to reopen closed work, implement, migrate, merge or spend.

Prefer good editorial results without mandatory paid AI APIs. Economic preference is not a compulsory cascade of local/server/external models. Reuse valid work, escalate only for a concrete need within authorization, and verify exact-version licensing, provider terms and commercial distribution eligibility before incorporation or advertising. Keep unresolved model, capability and cost claims explicitly pending.

## Execution feasibility before product approval

Before proposing a feature or refinement for adoption, verify the relevant actual baseline, contracts, implementation and test evidence. Distinguish available end-to-end behavior, existing primitives needing integration, internal extensions and external/research dependencies. General upstream capability, an engine name or an unconnected interface is not proof that CEVRA already delivers the result. Keep unverified capabilities explicit.

When a proposal exceeds existing capabilities, disclose the minimum additional implementation, affected components, dependencies, expected resource/cost/complexity/maintenance and commercial implications before asking the product owner to adopt it. Include a simpler alternative where viable and fix-now versus defer reasoning. This assessment can change adoption; it is not a detail to postpone until after approval. Do not invent effort or performance numbers. See section 11.4 of `docs/CEVRA_EDITORIAL_DECISIONS.md`.

Accumulate justified Media Runtime gaps in the coordinated inventory in section 16 of that record and propose the bounded extension phase before dependent implementation. Do not modify the closed runtime during a product discussion. Consolidated planning does not require a big-bang rewrite or one giant PR: preserve incremental tests/review, compatibility, typed allow-listed execution and lifecycle guarantees. Report an immediate dependency or material cost/security conflict before silently deferring it; unrelated safe work may continue. New engines, FFmpeg source/version changes, external services and advanced restoration are not implicitly authorized by this inventory.

## Product-owner acceptance test catalog

`docs/CEVRA_PRODUCT_OWNER_ACCEPTANCE_TESTS.md` is the cumulative manual acceptance catalog for approved product behavior. When an approved decision introduces testable behavior, changes a parameter, supersedes a prior expectation or adds an integration path, update that catalog in the same documentation change whenever practical.

Do not merely append duplicate tests. Reuse stable test IDs, revise the action/expected result when a newer approved decision changes the requirement, and preserve traceability to the decisions involved. Before every Product Owner test build, derive the executable checklist from the catalog, identify BLOCKED tests honestly, list required fixtures, and state which prior tests must be repeated because the implementation changed. CI/unit tests complement but do not replace relevant Product Owner acceptance tests.

Use the response vocabulary defined in the catalog (`PASS`, `PARTIAL`, `FAIL`, `BLOCKED`; and `APROVADO`/`REPROVADO` for subjective quality). Do not declare a feature homologated solely because it compiles or because automated tests pass.
